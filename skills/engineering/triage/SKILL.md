# 分诊（triage）

把项目 issue tracker 上的 issue 推进过一台由分诊角色组成的小型状态机。

如果本仓库把外部 pull request 也当作请求入口（见 issue-tracker 配置），分诊同样覆盖它们：**PR 就是一条附带代码的 issue**，使用同样的角色、同样的状态、同一台状态机，只有少数差异在下文以“针对 PR”标注。裸写的 `#42` 依照 tracker 配置解析为 issue 或 PR。

分诊期间发到 issue tracker 的每条评论和每个 issue **必须**以下面这条免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写出耐久的代理简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者补充更多信息
- `ready-for-agent`：规格完备，AFK 代理可以直接接手
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对 PR 而言，同样的状态针对附带的代码来解读：`ready-for-agent` 表示已附带简报、代理应对 diff 采取下一步动作；`ready-for-human` 表示可以由人来合并了。

每个完成分诊的 issue 应当恰好带一个类别角色和一个状态角色。如果状态角色互相冲突，先标记出来并询问维护者，再做其他任何事。

这些是规范的角色名。issue tracker 里实际使用的标签字符串可能不同。映射关系应当已经提供给你。如果没有，让用户运行 `/setup-skills`。

状态流转：没有标签的 issue 通常先进入 `needs-triage`；再从那里转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖流转；对看起来不寻常的流转，先标记并询问，再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述想要什么。理解请求并行动。示例：

- “给我看所有需要我关注的东西”
- “我们看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “哪些已经可以让代理接手了？”

## 展示需要关注的内容

查询 issue tracker，按最旧优先展示三个桶：

1. **未打标签**：从未分诊。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊记录后报告者有新动作**：需要重新评估。

当 PR 在范围内时，把外部 PR 也放进这些桶，并在每行标注 `[PR]` 或 `[issue]`。发现环节只列出*外部* PR（谁算外部由 tracker 配置定义），所以协作者进行中的 PR 不算分诊工作。这个过滤只用于发现环节；被明确点名的 PR 无论如何都要分诊，不论作者是谁。

展示数量统计和每项的一行摘要。让维护者挑选。

## 分诊某个具体的 issue 或 PR

1. **收集上下文。**读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析已有的分诊记录，避免重复追问已解决的问题。借助项目的领域词汇表探索代码库，尊重相关领域的 ADR。对照代码库做两项检查：(a) **重复（redundancy）**：按领域概念（而非请求的措辞）搜索请求的行为是否已有实现，并报告你查过哪些地方。如果找到，这就是一次“已实现”的 `wontfix`（见第 5 步）。(b) **既往拒绝（prior rejection）**：读 `.out-of-scope/*.md`，列出所有与该请求相似的条目。

2. **给出建议。**把你的类别和状态建议连同理由告诉维护者，并附上与请求相关的代码库简报（包括是否已经实现）。等待指示。

3. **验证主张。**在拷问之前，先检查主张是否站得住。对 bug，按报告者的步骤复现它。对 PR，确认 diff 做了它声称的事：checkout 出来，跑相关的测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（`needs-info` 的强烈信号）。一次已确认的验证能让代理简报强得多。

4. **拷问（grilling，如有需要）。**如果请求需要充实，调用两次 Skill 工具，传入 “grilling” 和 “domain-modeling”，一次一个问题地把它拷问成形，锤炼领域术语，并在决策落定时顺手更新 `CONTEXT.md` 和 ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与代理简报相同，但要说明为什么无法委托出去（需要判断、需要外部访问、设计决策、手动测试）。
   - `needs-info`：发分诊记录（模板见下文）。
   - 对 `wontfix`，关闭 issue，评论内容取决于*为什么*关闭：
     - **已实现**：变更已存在于代码库。指出它在哪里；**不要**写入 `.out-of-scope/`（该知识库记录的是*被拒绝*的请求，不是已建成的功能）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论里链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。如有部分进展，可选择性发评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent”，信任他们并直接应用该角色。确认你即将做的事（改角色、发评论、关闭），然后行动。跳过拷问。如果没有经过拷问就把状态改为 `ready-for-agent`，询问是否要写一份代理简报。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问中确定的所有内容都记到“目前确认的信息”下，以免成果丢失。问题必须具体、可执行，不能只写“请提供更多信息”。

## 恢复上一次会话

如果 issue 或 PR 上已有分诊记录，先读它们，检查报告者是否回答了悬而未决的问题，并在继续之前给出更新后的全景。不要重复追问已解决的问题。
