# Ask Me

你记不住每个技能，所以来问。

**流程（flow）**是穿过这些技能的一条路径。大多数路径沿一条**主流程**行进，两条**入口流程（on-ramp）**汇入其中。其余要么是独立技能，要么是垫在下层的词汇层。

## 主流程：想法 → 上线

大多数工作走的路线。你有一个想法，想让它被建出来。

1. **`/grill-with-docs`** 用访谈把想法磨锐利。只要你在**某个工作目录里干活**，就从这里开始：它有状态，把学到的东西留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见 Standalone 一节。两者跑的是同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，所以只要有个仓库可留，它就是两者中更好的那个。）
2. **分支：所有问题都能在对话里解决吗？**如果某个问题需要一个可运行的答案（状态、业务逻辑、必须亲眼看一下的 UI），绕道走一次原型，用 **`/handoff`** 在两个方向架桥（原型住在自己的目录里，这正是 `/handoff` 的用途；见 Phase boundaries 一节）：
   - **`/handoff`** 出去，然后对着那个文件开一个全新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 把学到的东西带回来，并在最初的想法串里引用它。
3. **分支：这是不是一个要多会话的构建？**
   - **是** → **`/to-spec`**（把对话串变成规格（spec）），然后 **`/to-tickets`** 把它拆成一张张曳光弹（tracer bullet）工单，每张工单声明自己的**阻塞边**。在本地 tracker 上，每张工单是 `.scratch/<feature>/issues/` 下的一个文件，手工按“阻塞者优先”的顺序处理；在真实 tracker 上，这些边变成原生的阻塞链接，于是任何阻塞已完成的工单都能被领走：每张工单启动一次 **`/implement`**，**每张之间用 `/clear` 清空上下文**。每张工单自包含，所以上一张的上下文用完即弃。
   - **否** → 就在这里，同一个上下文窗口里 **`/implement`**。

   无论如何，**`/implement`** 构建每个 issue 的方式是内部驱动 **`/tdd`**（一次一个 red-green 切片），然后在提交前跑 **`/code-review`** 收尾，即对 diff 做一次双轴评审（Standards + Spec）。只想测试先行地构建一个具体行为、不需要完整规格时，单独用 **`/tdd`**；想对照某个固定基准评审分支或 PR 时，单独用 **`/code-review`**。

### 上下文卫生

把第 1 到第 3 步保持在**一个不间断的上下文窗口**里（`/to-tickets` 之前不要 compact 也不要 clear），让拷问（grilling）、规格和工单都建立在同一份思考之上。之后的每次 `/implement` 都从全新上下文开始，从工单出发。

这件事的上限是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（在当前最先进的模型上约 150k token）。如果会话在 `/to-tickets` 之前逼近它，不要在退化状态下硬撑；在最近的一个阶段边界 `/compact`，然后继续（见 Phase boundaries 一节）。

## 入口流程（on-ramps）

一种会生成工作的起始处境，随后汇入主流程。

- **bug 和请求越积越多** → **`/triage`**。它把 issue 推进过分诊角色，产出代理可直接接手的 issue，之后由 **`/implement`** 领走。

  分诊只用于**不是你创建的** issue：bug 报告、送上门的功能请求、一切以原始形态到达的东西。`/to-tickets` 产出的工单已经代理就绪，所以**不要分诊它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。对付难缠的：第一眼看不出门道的 bug、间歇性闪失、在两个已知良好状态之间悄悄溜进来的回归。它在拿到**紧凑的反馈循环**（一条已经能在这个 bug 上变红的命令）之前拒绝空谈理论，然后用回归测试修复。当真正的发现是没有好的接缝（seam）能锁死这个 bug 时，它的事后分析会交接给 **`/improve-codebase-architecture`**。

- **巨大而多雾的事项：全新项目或超大型功能构建，一个会话装不下** → **`/wayfinder`**，这里认知负担最重的流程。当从这里到目的地的路还看不见时，它在 issue tracker 上绘制一张由**决策工单**组成的**共享地图**，逐张解决，产出**决定，而不是交付物**，直到迷雾被推回去、路清晰起来。**`/grill-with-docs`** 磨锐利的是一个会话装得下的想法；wayfinder 是给装不下的那个准备的，它更慢也更密，所以只把它用在恰好这种地方，绝不用在范围清晰的功能上。

  地图清晰之后，**它负责交接，不负责建造**：在 **`/to-spec`** 处汇入主流程，它把地图里链接的决定收拢成一份可建造的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接接进 `/implement` 会跳过这次收拢、把链接的细节扔掉，所以只有当事项真的很小的时候才直接 `/implement`。

## 代码库健康

不是功能开发，只是保养。

- **`/improve-codebase-architecture`** 在你有空的时候就跑一次，让代码库保持适合代理在其中运作。它会浮出**深化机会（deepening opportunities）**；选中一个就_生成了一个想法_，你可以带着它从 `/grill-with-docs` 进入主流程。它是找出候选者的勘查；**`/codebase-design`**（见下）是你对选中者做设计的操作台。

## 垫在下面的词汇

两个模型调用（model-invoked）的参考技能，*垫在*其他技能下面运行，各自是其词汇的唯一事实来源。当问题出在**词**而不是流程上时，直接调用它们；或者让上面的技能把它们带进来。

- **`/domain-modeling`**：磨锐利项目的*领域*语言：挑战一个模糊的术语、解决一个超载的词（“account” 一词三用）、把难以逆转的决定记录成 ADR。它是 `/grill-with-docs` 驱动的那门现场纪律，让 `CONTEXT.md` 保持为一本干净的词汇表。
- **`/codebase-design`** 是深模块（deep module）词汇表（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的*形状*：在干净的接缝（seam）上，用小接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这门语言。

## Phase boundaries

**阶段（phase）**是会话内部的一块工作：拷问（grilling）、实现、QA。在两者的**边界**上你有五个选项，而在它们之间挑选是整张地图里最模糊的决定：

- **Continue**：原地不动。零成本，零损失。
- **`/clear`**：清空窗口，用于这里的东西对下一步毫无价值的时刻。
- **`/handoff`** 写出一个可携带的 markdown 文件。窄：只用于**新 harness**、**新目录**、**同事**，或在**阶段中途**分出一个支线任务。它买到的是可携带性。
- **子代理（subagent）**：把一个范围收紧的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** 压缩当前上下文，并用它播种一个全新会话。**默认项**，位于决策树的底部，而不是第一个伸手去够的。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看那棵有序的树：五个问题、每个分支背后的推理，以及为什么一手来源的代价让 **Continue** 成了最先要排除的选项。在**边界上**做这个决定；阶段中途，要么继续，要么把剩下的拆给子代理。

## Standalone

完全游离于主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 相同的不留情面的访谈，但**无状态**：本地什么也不保存，也不构建 `CONTEXT.md`。当你**不在工作目录里干活**时用它（磨锐利一个计划、一份设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录里，改用 `/grill-with-docs`：它跑同样的访谈还留下书面记录，严格来说是更好的那个。
- **`/grilling`** 是访谈原语本身：一次一个问题、前沿（frontier）、事实归代理管、决定归你管。`/grill-me` 和 `/grill-with-docs` 是进入它的两个具名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要一场没有任何包装的访谈时才直接调用它。
- **`/resolving-merge-conflicts`** 逐个 hunk 地处理进行中的 merge 或 rebase 冲突，按**意图**解决，每个决定追溯到两侧各自的一手来源，而不是靠挑哪几行，然后完成整个操作。它从不运行 `--abort`。独立于所有流程之外：当你已经身处冲突之中时调用它。
- **`/prototype`** 是一个一次性的小程序，回答一个设计问题：这个状态模型手感对不对，或这个 UI 该长什么样。一次性是对代码写法的约束，不是销毁它的承诺：答案折叠进真正的代码，原型本身则作为**一手来源**保存在 main 之外的一条 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步里的那次绕道，但任何设计问题在纸面上难以落定时都可以调用它。
- **`/research`**：把阅读跑腿的活委托给**后台代理（background agent）**：它对着**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是要*带进*主流程、拿到 `/grill-with-docs` 用的，因为调研喂养思考，而不是取代思考。
- **`/to-questionnaire`** 在卡住你的东西不在你脑子里也不在代码库里、而在**别人**脑子里时登场，它替你写一份问卷让对方填。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**这次发送**访谈你（发给谁、要拿回什么），并把问题瞄准缺口。收回来的东西是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 用于只有**人类**能做的步骤：开通基础设施、配置凭据或 CI secrets、在一个陌生的第三方控制台里点来点去、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、抓取每个值并写进 `.env` 和 GitHub secrets，让这套流程不再是你每次都要向代理重新解释的东西。它是模型调用（model-invoked）的，所以代理一撞上只有你能过的墙就会伸手拿它。如果代理自己就能做，那就该它自己做；这个技能用于人类真正在环内的场合。
- **`/wait-what`** 是对一条没讲明白的消息的纠正。在对话中途、任何其他技能内部使用它，代理会用你缺的那份上下文、用平实语言、按 `CONTEXT.md` 的词汇，把它刚说的重新讲一遍。它是事后起作用的；`/grill-with-docs` 是事前药方，因为提前约定的共享语言能让行话根本不出现。
- **`/teach`**：跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是撰写供代理消费的文档的参考：技能、AGENTS.md、被指向的文档。

## Precondition

**`/setup-skills`**：在第一个工程流程之前运行，配置其他技能默认依赖的 issue tracker、分诊标签和文档布局。自定义 issue tracker 也可以。
