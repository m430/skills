# UI 原型

在单个路由上生成**几个截然不同的 UI 变体**，通过一条浮动底栏切换。用户在浏览器里翻看各变体，挑一个（或从每个里偷一些），然后把其余的扔掉。

如果问题关于逻辑/状态而不是外观，那就选错了分支。用 [LOGIC.md](LOGIC.md)。

## 什么情况下这是正确的形态

- “这个页面应该长什么样？”
- “我想在定下来之前看看这个 dashboard 的几个方案。”
- “给设置页试一种不一样的布局。”
- 任何本来要让用户花一整天、在脑中三个模糊设计稿之间做选择的情形。

## 两种子形态：强烈优先选子形态 A

UI 原型在**紧挨着应用其余部分**时容易判断得多：真实的 header、真实的侧栏、真实的数据、真实的信息密度。孤零零的一次性路由是个真空：每个变体在隔离状态下看着都不错。只要有说得通的现有页面能承载变体，就默认子形态 A。只有当原型确实找不到可以落脚的邻近页面时，才动用子形态 B。

### 子形态 A：对现有页面的调整（优先）

路由已经存在。变体渲染在**同一路由**上，由 `?variant=` URL 查询参数门控。现有的数据获取、参数和鉴权全部保留，只有渲染部分替换。这是默认选择；除非有具体理由，否则选它。

如果原型针对的东西还没有页面，但*天然应该长在某个页面里*（dashboard 的新区块、设置页的新卡片、现有流程的新步骤），这仍然算子形态 A。把变体挂载在宿主页面里。

### 子形态 B：新页面（最后手段）

只有当被原型化的东西确实没有可以落脚的现有页面时才用（比如一个全新的顶层界面，或一个没法合理嵌入任何地方的流程）。

按项目已有的路由约定创建一个**一次性路由**。不要发明新的顶层结构。命名让人一眼看出它是原型（比如在路径或文件名里带上 `prototype` 一词）。同样用 `?variant=` 模式。

选定子形态 B 之前先自检：真的没有可以嵌入的现有页面吗？空路由会掩盖那些有真实内容的页面会暴露的设计问题。

两种子形态下的浮动底栏完全相同。

## 流程

### 1. 写明问题并选定 N

默认 **3 个变体**。超过 5 个就不再截然不同，开始变成噪音，所以上限设在 5。

用一行字写下计划，放在原型所在位置或文件顶部注释里：

> “设置页的三个变体，经 `?variant=` 切换，放在现有 `/settings` 路由上。”

无论用户在不在场反驳，这个做法都有效。

### 2. 生成截然不同的变体

逐一起草变体。用这些标准衡量每一个：

- 页面的目的，以及它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 清晰的导出组件名，比如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层级、不同的主要交互入口，而不只是不同配色。三个微调过的卡片网格不是 UI 原型，是墙纸。如果两稿太像，就重做一稿，并明确给出“不要用卡片网格”这类指引。

### 3. 把它们接起来

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把所有现有数据获取保留在切换器上方；每个变体只替换渲染出来的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建浮动切换器

屏幕底部居中的一条小型固定定位栏，由三部分组成：

- **左箭头**：循环切到上一个变体（首尾相连）。
- **变体标签**：显示当前变体的键；如果变体导出了名字，也一并显示。比如 `B (Sidebar layout)`。
- **右箭头**：向后循环（首尾相连）。

行为：

- 点击箭头会更新 URL 查询参数（用框架的路由器，比如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可分享、刷新后状态不丢。
- 键盘：`←` 和 `→` 方向键也能循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面区分开（比如高对比度的胶囊形、淡淡的阴影），让人一眼看出它不是被评估的设计的一部分。
- 在生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查做门控，避免某次意外的原型合并把这条栏带给用户。

把切换器放进一个共享组件，让两种子形态都能复用。放在项目里存放共享 UI 的位置。

### 5. 交出去

把 URL（以及 `?variant=` 的各个键）给到用户。他们有空时会自己翻看。最有价值的反馈通常是**“我要 B 的 header 配 C 的侧栏”**，那才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出后，先记录答案（哪个变体以及为什么），再按 [SKILL](SKILL.md) 描述的方式留存原型。把胜者合入真实代码，其余的移到一次性分支上，不进 main：

- **子形态 A**：把胜者合入现有页面；从 main 上删掉落选变体和切换器。
- **子形态 B**：把胜出变体提升为真实路由；从 main 上删掉一次性路由和切换器。

完整的变体集合就是一手资料，所以要落到一次性分支，而不是直接进垃圾桶：留在 main 分支里的变体组件和切换器很快就会腐烂，迷惑下一个读代码的人。

## 反模式

- **只在配色或文案上有差别的变体。** 那是微调，不是原型。真正的变体在结构上彼此分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 就失去了意义。每个变体都应该可以自由推翻布局。
- **把变体接到真实的变更操作上。** 只读原型没问题。如果某个变体需要变更，就把它指向一个 stub：问题在于“该长什么样”，不是“后端能不能用”。
- **把原型直接晋升进生产。** 变体代码是在原型约束下写的（没有测试、最少错误处理）。合入时按正式标准重写。
